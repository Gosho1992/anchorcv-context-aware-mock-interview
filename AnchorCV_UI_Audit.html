1. Executive summary

The AnchorCV web app is functional, the data model is solid, and the loading-state copy has more personality than most products. The reason it feels "boring and difficult to use" is not one big problem — it's the accumulation of about a dozen small decisions, almost all fixable without changing the underlying React architecture.

The top-level findings are:

  • There is no onboarding. A first-time user signs up, is sent straight to a payment page, then dropped onto a dashboard with four identical-looking text cards and no instruction on what to do next. The product has no first-run flow, no example CV, no "try it once" path, no tooltips, no progress indicator across steps.
  • The visual design is generic 2023 SaaS dark mode. Indigo gradients on dark navy, Georgia serif headings, "AI-powered" tagline, no imagery, no illustrations, no logo mark beyond a generic anchor SVG, no animation other than a spinning gear emoji. Nothing on the screen tells you it's this product and not one of fifty interchangeable resume tools.
  • The two core features (Analysis and Builder) overlap and compete. Both ask the user to upload a CV and paste a job description. Both produce a result on the right of a 2-column layout. New users have no way to know which one they should do first, or whether they need both.
  • Inline styles fight the CSS. About 40% of the visual styling lives in inline style={{ ... }} blocks, not in globals.css. The Dashboard's premium card, the Payment Success extension prompt, the Analysis page's score circles and badges, and several others use ad-hoc colors and corner radii that don't match the rest of the app. This is the reason it looks visually inconsistent even though the components are individually fine.
  • The app's idea of "premium" is invisible until you click around. Pricing is never shown. The cost ($9? $29?), what you get, how long it lasts (90 days, hidden in the code), and what "Premium" unlocks vs. the free tier — none of this is on the marketing surface. The Payment page just says "Complete payment to unlock the app" with a button.
  • Tailwind is installed but not used. tailwind.config.js is present, postcss is configured, but no JSX file uses Tailwind utility classes. All styling is either custom CSS in globals.css or inline. This is dead weight and a maintenance trap (whoever joins the team will assume Tailwind classes exist).
  • Errors use window.alert() in three places (FilesPage, Analysis save, Builder save). Native browser alert dialogs are the most jarring UX you can ship in 2026.
  • The Files page renders a literal replacement character. Line 105 of FilesPage.jsx: {Math.round(...)} KB � {formatFileDate(...)} — a corrupted bullet separator. Every file row shows a black diamond with a question mark.

The good news: the React component model, Zustand store, TanStack Query usage, and routing are all clean. The audit below is about presentation, copy, flow, and polish, not architecture. None of the issues require rewriting the data layer.

4. Onboarding (the missing layer)

This is the single biggest gap. Below is the actual first-time user journey, traced through the code:

  1. Lands on /login — sees a card with two tabs (Login / Register). No marketing context. No screenshot of the product. No price. No "what is this?" Just a form.
  2. Clicks Register, fills first name, last name, country (free text input), email, password. No password strength meter, no email verification, no Terms-of-Service checkbox.
  3. Submits. Backend creates the row. Frontend immediately calls navigate("/payment", { autoStartCheckout: true }) — meaning the user is bounced straight to Lemon Squeezy without ever seeing the app.
  4. Pays. Comes back to /payment-success, sees a "🎉 Premium Activated!" card with a 10-second auto-redirect countdown and one CTA: "Add Chrome Extension".
  5. Lands on / (Dashboard). Sees:
    • "Welcome back, <FirstName>." (lying — this is the first visit)
    • A teal "Chrome Extension — Premium Active" card with one CTA
    • Four identical-looking text cards: Resume Intelligence / CV Builder / My Files / Account & Billing
    No instruction on which to click. No "Step 1 / Step 2". No example CV. No empty-state nudge.
  6. Clicks "Resume Intelligence" (a guess), arrives at Analysis page. Two empty file dropzones, a select with 6 cryptic options ("Application Strategy", "ATS Score & Keywords"…), a textarea, a button. No explanation of what each output type does or which to pick first.
Net result: a paying user gets onto the dashboard knowing two things — that they spent money, and that there’s a Chrome extension. They don’t know what the app does, in what order, or how to get their first useful output. This is the source of the "difficult to use" feedback.

What the codebase has (or doesn’t) for onboarding

  • No tour library (e.g., react-joyride, intro.js, shepherd.js) installed
  • No "first time?" flag stored on the user (no onboarded_at, no has_completed_first_analysis)
  • No checklist component anywhere
  • No sample/demo data path — you cannot preview the analysis without uploading a real CV first
  • No "?" help icons, no tooltips, no contextual hints

5. Page-by-page audit, with mockups

The mockups below are SVG renderings derived directly from the JSX and CSS in the repository — same colors, same typography hierarchy, same component placement. They are approximate (no live data) but accurately represent the layout and visual feel the user experiences today.

5.1 Login / Register — src/pages/LoginPage.jsx

Login page (mocked from JSX). The card is centered on a dark background with two soft indigo radial gradients.

What works

  • Card is correctly centered, breathable padding, clear hierarchy.
  • Segmented control for login/register is the right pattern for a small app.
  • Error normalisation (getReadableError) handles weird FastAPI 422 response shapes correctly.

What doesn’t

  • Zero marketing context. A first-time visitor sees only a form. No sentence about what AnchorCV does, what it costs, what makes it different. Compare to e.g. Notion’s login — even their minimal login page has product collateral on the side.
  • Country is a free-text input. Should be a select. The backend uses it to set Lemon Squeezy billing context, so a typo could break tax handling.
  • No password show/hide toggle.
  • No "Forgot password?" link. If the backend doesn’t support reset (and from the auth router, it doesn’t), this is a real liability — users will forget passwords, especially after a 90-day premium gap.
  • No social login. Google sign-in alone would remove the registration-form barrier for ~70% of international students who already have a Google account.
  • No Terms-of-Service / Privacy checkbox. Required in EU and increasingly elsewhere.
  • Eyebrow uses a single anchor emoji ⚓ as the brand mark — renders inconsistently across platforms (sometimes outlined, sometimes blue, sometimes a shipping container).
  • Same screen handles login and register. The register variant adds three inputs (first name, last name, country) but the title still says "Welcome back." — copy never updates for new users.

5.2 Payment — src/pages/PaymentPage.jsx

Payment page. One headline, one subline, one button. No price, no feature list, no testimonial.

What works

  • Auto-redirect to Lemon Squeezy when arriving via the register flow (state.autoStartCheckout) — fewer clicks for new users.
  • Button is disabled while redirecting, giving visual feedback.

What doesn’t

  • The price is invisible. Nowhere in the JSX (or the dashboard, or the login page) does the user see a dollar amount before they are sent to Lemon Squeezy.
  • No feature comparison. "Premium gives you full dashboard access for 90 days" doesn’t say vs. what. There’s no free tier described, so the message reads as "pay to use the app at all" — which is actually accurate but a hard sell.
  • No social proof, money-back guarantee, or risk reversal. No testimonials, no "join 1,000+ students", no refund policy.
  • "90 days" is buried in microcopy. Users will likely interpret this as "subscription" rather than "one-time access".
  • The CTA name leaks the payment vendor. "Continue to Lemon Squeezy checkout" — users have never heard of Lemon Squeezy and the brand intrusion makes the moment feel less polished. "Continue to secure checkout" would be cleaner.

5.3 Payment success — src/pages/PaymentSuccessPage.jsx

Payment success page. Auto-redirects after 10 seconds.

What works

  • Optimistic local update: even before the backend webhook fires, the local user state flips is_premium=true so the next page already trusts it.
  • Auto-redirect with manual "Go now" escape — correct UX pattern.
  • The Chrome extension card is the right place to put this prompt — the user’s motivation is highest right after they’ve paid.

What doesn’t

  • The teal extension card is the only thing on screen, so a user who doesn’t want the extension feels like the page wasn’t built for them. There’s no "Or jump to your dashboard" alternative CTA at the same visual weight.
  • The Chrome extension card uses 8px corner radius and 14px font, while everything else in the app uses 14–24px radius and 13/15/16px text. It looks like a foreign component.
  • Confetti emoji as the celebration moment. Functional, but a tiny bit of CSS animation (a checkmark drawing in, or a single confetti burst) would make this moment land emotionally.
  • No receipt link, no order ID, no "Email confirmation sent to…" reassurance. Payment-success pages should always confirm the transaction in writing.

5.4 Dashboard — src/pages/DashboardPage.jsx

Dashboard for a premium user. Sidebar nav on the left, hero panel + Chrome extension card + 4 feature cards on the right.

What works

  • Sidebar layout collapses cleanly on narrow viewports (one media query at 960px).
  • Premium / non-premium variants of the Chrome extension card are well-handled with one ternary.
  • Cards are full clickable areas (using <Link>), which is the right pattern.

What doesn’t

  • Welcome message lies on first visit. "Welcome back" should be "Welcome to AnchorCV" the first time. There’s no has_logged_in_before check anywhere.
  • The four cards all look identical. Same color, same shape, same icon (none). The user can’t tell which to click first. They have no visual hierarchy and they don’t convey what each does — the descriptions are the only differentiator.
  • The cards have no icons or imagery. Even one carefully-chosen emoji per card (or a small SVG glyph) would let the user’s eye scan instead of read.
  • Order is wrong. "Resume Intelligence" comes first — but the natural first action for most users is to build a CV (or upload one for analysis). Either way, "Account & Billing" should never be a fourth-equal option on the dashboard; it belongs in the sidebar account card or as a small link in the corner.
  • The sidebar shows the brand twice. Once as eyebrow ("⚓ ANCHORCV") and once as Georgia serif h1 ("AnchorCV"). Pick one.
  • No "recent activity" or "your last analysis" widget. A returning user has no shortcut back to where they left off — they have to re-navigate.
  • No usage stats on the dashboard. "You’ve generated 3 analyses this week" or "5 days of premium remaining" would give the dashboard a reason to exist beyond being a navigation menu.

5.5 Resume Intelligence (Analysis) — src/pages/AnalysisPage.jsx

Analysis page (initial state). Sidebar + hero + 2-column form/result layout.

What works

  • The two-column form/result layout is the right pattern for this kind of tool.
  • Result is persisted in Zustand, so navigating away and back doesn’t lose work.
  • Output type select is conditional — "Resume Improvement" exposes a fallback questions panel (industry/level/goal) when no JD is supplied.
  • "Save to Cloud" wires together backend PDF export + storage upload, which is genuinely useful.
  • Loading state ("✨ Analysing your CV against the role requirements…") is the most personable UI moment in the entire app — cycles through 10 quotes every 3 seconds.

What doesn’t

  • Six output types in one select with no explanation. Application Strategy, ATS Score & Keywords, Resume Improvement, Job Match Score, Cover Letter, Email to Professor — the new user has no way to know which to pick. This screen needs either a stepper, pickable cards (like the Builder uses for formats), or at minimum a tooltip per option.
  • Both file inputs are labeled "Choose a resume file" regardless of whether the dropzone is for the resume or for the job description. Look at FileDropzone.jsx line 14: the strong text is hard-coded. The eyebrow label changes ("Resume upload" vs "Job / Scholarship Requirements") but the bold "Choose a resume file" string never changes. Confusing.
  • The "dropzone" is not actually a dropzone. No drag-and-drop handler is bound. The component just wraps a native file input in a styled label. Keep the name FileDropzone, but it needs a real onDrop handler.
  • The result panel hosts AI HTML inside a white card (preview-panel with background: white), which clashes hard with the surrounding dark theme. There is no "preview / dark / light" toggle.
  • The Mojibake map is a smoking gun. Lines 10–19: a hand-curated list of broken UTF-8 patterns (Ã© → é, â€™ → right-quote, etc.). This means the rendered output sometimes shows broken characters before this client-side patch fixes them. The real fix is upstream encoding; this hack masks the symptom.
  • Score circles, badges, banners, and the entire MatchScoreCard are written with inline styles. The component is 800+ lines long because of this. Would be 300 if extracted into reusable styled components.
  • The "Job Match Score" output renders a totally different React subtree (MatchScoreCard) than every other output type (which all render dangerouslySetInnerHTML). Two paths through the same screen, two visual languages.
  • "Use in CV Builder" button only appears for 3 of 6 output types. The decision is buried in showBuilderButton at line 489 — it’s correct but invisible logic that surprises the user.

5.6 CV Builder — src/pages/BuilderPage.jsx

Builder page. Two columns: configuration form on the left, white preview frame on the right.

What works

  • Format selector cards (FormatCard) are the right pattern — visual, scannable, with a clear selected state.
  • Live preview as iframe with srcDoc means the generated HTML can’t pollute the parent.
  • State persistence across navigation (Zustand) is preserved here too.
  • "Use latest analysis" button to import the Analysis output as Builder guidance is a thoughtful cross-feature link.

What doesn’t

  • The form is dauntingly long. Resume upload, format select, target role, requirements textarea, prefill panel, three more selects (tone/language/length), color picker, sections checkboxes, AI enhance checkbox, two buttons. There is no progressive disclosure — every option is visible the first time.
  • Native HTML <input type="color"> for the accent color picker is one of the ugliest input controls in the browser. Looks different in every OS. Replace with a small palette of preset swatches.
  • Sections checkboxes are unnamed in the JSX — they’re generated by mapping over Object.entries(sections), which means whatever the store calls them (likely summary, experience, education, skills…) shows up verbatim, including capitalisation.
  • Tone select has only 3 options (Professional / Academic / Concise), language has 7, length has 3 — but they’re three identical-looking selects in a row. No visual cue that one is more important than another.
  • "AI enhance" is a checkbox with no explanation. What does it do? When should I check it? The user has no way to know.
  • Empty preview shows nothing — just white space. A wireframe placeholder (a fake CV silhouette) would tell the user what they’re about to get.
  • "Build CV" is the only path forward, but the form takes ~12 fields. A "use sample data" button to let users see the result in 5 seconds would dramatically lower the friction for first-time use.

5.7 My Files — src/pages/FilesPage.jsx

Files page. Native file input, then a flat list of stored files. The square character represents the literal � replacement character that appears in production.

What works

  • List rows are clean: name + size + date on the left, three actions on the right.
  • HTML files are smartly opened via blob URL in a new tab so they render rather than download.
  • TanStack Query handles the file list, refresh on upload, refresh on delete.

What doesn’t

  • BUG: a literal replacement character (�) renders as the separator between size and date. Look at FilesPage.jsx line 105: 
    {Math.round((storedFile.size_bytes || 0) / 1024)} KB � {formatFileDate(storedFile.created_at)}
    That’s a corrupted middle-dot. Replace with &middot; or · or just a hyphen.
  • Native <input type="file"> shows the OS-default "Choose File" button which doesn’t match anything else in the app.
  • Delete is destructive and instant — no confirmation. One stray click and the file is gone with no undo.
  • No icons. A PDF, a DOCX, and a TXT all look identical — the user has to read the extension.
  • No search, no filter, no sort. Once a user has 30 files, this list becomes unusable.
  • No file type pills (e.g., a small "PDF" or "DOCX" badge per row), no source pill (e.g., "from Builder" / "from Analysis").
  • Empty state is one passive sentence. "No files are stored yet." with no "Generate your first CV →" call to action.
  • Errors fall back to alert() (line 112: .catch((err) => alert(err.message))).

5.8 Account — src/pages/AccountPage.jsx

Account page. That’s the entire screen.

What works

  • Storage meter is the only place that uses the .meter primitive — visually pleasant.
  • Reuses the same auth + files queries as elsewhere — no separate API surface.

What doesn’t

  • This page is dramatically underbuilt. No "Change password", no "Update email", no "Delete account", no "Cancel subscription / Renew", no "Download my data", no "Notification preferences", no "Connected services", no "Billing history", no "Receipts".
  • The premium expiry date is shown as toLocaleDateString() with no countdown ("48 days left") — users have to do mental arithmetic.
  • "Payment required" appears as the eyebrow when premium is inactive, but with no CTA to do the payment. The user has to remember they need to navigate to /payment manually.

  • No Sign-out button on this page. Sign-out lives only in the sidebar account card. Users intuitively look for it on the Account page.

5.9 Loading & error states (cross-cutting)

Loading state (the best part of the app)

Both Analysis and Builder share a near-identical LoadingQuotes component — a 2.5rem spinning gear (CSS @keyframes spin) plus a cycling array of motivational quotes that swap every 3 seconds. The 10 quotes are warm, varied, and on-brand. This is the only piece of UI in the app that has a personality.

Don’t change this. It’s the strongest piece of UX in the product. Consider extracting LoadingQuotes into src/components/ so it’s reusable, and using it on slow operations elsewhere too (file upload, PDF export).

Error states

  • Three places use window.alert(): FilesPage.jsx:112, AnalysisPage.jsx:592, BuilderPage.jsx:199. Native browser modals are jarring and break the app’s visual language.
  • Other places use inline <p className="error-text"> — orange-pink text under the form. Better, but easy to miss.
  • No toast/notification system. A single shared toast container (e.g., react-hot-toast or sonner) would unify these patterns for ~30 lines of code.
  • Error normalisation is good. getReadableError in LoginPage and normalizeErrorDetail in api/client.js handle FastAPI’s 422 array shape correctly. This logic should be lifted to a shared util.
  • No empty-error-fallback for the API request. If the backend returns 500 with an HTML error page, the JSON parse fails silently and the user sees "Request failed."

5.10 Discovery NEW · May 2026

Sources: anchorcv-frontend/src/pages/DiscoveryPage.jsx, anchorcv-backend/app/routers/discovery.py, anchorcv-frontend/src/store/useCvWorkspaceStore.js (discovery… fields).

The Discovery feature is a free-text "what are you looking for?" entry point that turns into a personalised career landscape via GPT-4o-mini. It was added to solve the onboarding gap flagged in section 4 of this audit: a brand-new paying user now lands on Discovery instead of the bare dashboard, with a sample landscape pre-populated, so the first-time experience has something to react to instead of four identical menu cards.

Mockup

Discovery page (mocked). Sidebar has new "Discover" item, hero panel with input + Explore button + optional CV upload widget, sample-mode banner for first-time users, then summary, close matches, known programs (with "Analyse my CV" hand-off button), and a search-tags strip.

What it does (user-visible)

  • Free-text input. User types something like "electrical engineering, power systems, PhD in Germany" or picks one of four example queries shown as chips below the input.
  • Optional CV upload. A small "Upload your CV (optional)" panel directly under the input. PDFs, DOCX, and TXT are accepted. The text is parsed server-side, kept in the browser session only (not saved to Files), and used as additional context for the GPT prompt so the landscape personalises to the user’s actual experience.
  • Result is a structured landscape, not a free-text answer. Five blocks rendered as cards: a 3-4 sentence summary, 4-6 "Close matches" subfields with a Growing/Stable badge and "distance" estimate, 2-3 "Nearby" adjacent fields that require some upskilling, 1-3 "Known programs" pulled from a strict allowlist (DAAD, Commonwealth, Chevening, Fulbright, Erasmus Mundus, Marie Skłodowska-Curie, EPSRC, NSERC, JSPS, KAUST, Aga Khan Foundation, OFID), and 10-15 search tags as clickable Google query chips.
  • Hand-off into Analysis. Each "Known programs" card has an "Analyse my CV" button that pre-fills the program metadata into the Analysis page’s requirement textarea and navigates the user there. This is the only existing route from Discovery into the rest of the app.
  • Sample landscape for first-time users. Users whose onboarded_at is null see a hardcoded "Computer Science Master’s in Europe" landscape on first visit, with a purple banner reading "This is a sample landscape." All buttons in the sample (Analyse my CV, search tags, copy all) are disabled. The sample disappears the moment the user clicks Explore for real.
  • Persistent generation across navigation. Discovery state lives in the Zustand workspace store, not in local component state, so a user who clicks "Explore" then immediately navigates to Analysis sees the result waiting for them when they return to /discover. The OpenAI fetch keeps running in the background.
  • Regenerate button. Below the summary, bypasses the cache for the same query.
  • Cache "Loaded from cache" indicator shown when the response came back instantly from SQLite.

What it does (technical)

LayerImplementation
Backend routePOST /api/discover/landscape (Pydantic body), POST /api/discover/extract-resume (multipart upload), GET /api/discover not exposed
AuthDepends(get_current_user) — both endpoints reject anonymous calls with 401.
Rate limit20 calls/day for free users, 500/day for premium. Counter stored in SQLite (discovery_cache.db → daily_calls table).
CachingSQLite (landscape_cache table) keyed on hash of (lowercased query + first 1k chars of resume text). 24-hour TTL. Same query without resume and same query with resume yield different cache entries.
Allowlist enforcementHard-coded list of 12 programmes injected into the system prompt. Model is explicitly instructed not to invent programme names. If nothing matches, known_opportunities is returned empty and search_tags carry the gap.
ValidationNested Pydantic models (Subfield, AdjacentField, KnownOpportunity, LandscapeResponse) validate the GPT JSON shape before responding. Invalid shapes return 502 instead of leaking malformed JSON to the client.
Model + costgpt-4o-mini at temperature 0.7, response_format json_object, max_tokens 2000. ~$0.0012 per call. Resume context capped at 2000 chars in the prompt to control cost.

What works

  • The allowlist is the strongest decision. The original proposal allowed the model to invent programme names; tightening to a 12-item allowlist removed the single biggest reputational risk. The trade-off — missing some real-but-niche programmes — is acceptable for v1.
  • Format reuses the existing visual language (panel cards, eyebrows, primary-button gradient, two-up grid). Discovery doesn’t feel like a foreign component grafted on, unlike the teal Chrome-extension card called out in section 5.4.
  • The "distance_from_user" field ("close", "4-8 weeks", "3-6 months", "career shift") is unusually honest framing for an AI tool — it tells the user how far they are from a field rather than just listing options uncritically. Pairs with the "Credibility Guardian" personas already used in the analysis prompts.
  • Sample mode solves the empty-state problem flagged for the Files, Analysis result, and Builder preview panels in section 6.5. A first-time user has something concrete to react to.
  • Persistent state via Zustand matches the pattern already used for Analysis and Builder — one consistent way to handle long-running results.
  • Search tags as a fallback is honest about the LLM’s limits: when the model can’t name a specific programme, it gives the user the queries to find live calls themselves.

What doesn’t (yet)

  • No quota counter visible to the user. A free user can hit the 20-call cap silently and only learn about it from a 429 response. A small "X of 20 today" chip somewhere on the page would set expectations.
  • Resume widget UI is plain. No progress bar during upload, no preview of which sections of the CV were actually used, no way to choose a previously-uploaded resume from Files. Day-1 acceptable but a clear v2 improvement.
  • Sample-mode banner is the only visual cue; the cards and search tags are dimmed and disabled but visually still look "real." A more deliberate "demo" treatment (watermark, dotted border, "Example" badge per card) would prevent confusion.
  • No analytics on what people search for. Queries are hashed and logged to the SQLite query_log table but there’s no UI to view them. This is the highest-value data the app could collect — tells you exactly which integrations to build next.
  • Single-server cache. SQLite cache is fine for the current single-host deployment; if this scales horizontally, each box gets its own cache and quota counter, effectively doubling a user’s daily limit. Migrate to Redis when you do.
  • No "Suggest a programme" path. If a user knows of a real programme not in the allowlist (e.g., specific national funding bodies), there’s no way to surface it. A simple form that creates a moderation entry would grow the list safely.
  • Sample landscape is hardcoded for "Computer Science Master’s in Europe." Engineering students, medical students, social scientists all see the same sample. A field-aware sample (rotated based on user’s registered country/interest, or selected from 4-5 hand-curated samples) would feel more personal.
  • No content moderation. A user could type any query (including off-topic or adversarial ones) and the model will respond. Not a live problem at current volume; budget a moderation pass before public launch.
  • Loading state is just the button text changing. No skeleton cards, no progress indicator while the OpenAI call is in flight. The "Loading quotes" component used on Analysis and Builder would fit nicely here.

How it changes the IA

The sidebar now has six items (Dashboard, Discover, Analysis, Builder, Files, Account). The intended hierarchy is Discover → Analysis → Builder: Discover surfaces an opportunity, Analysis evaluates fit against the candidate’s CV, Builder produces the deliverable. The "Analyse my CV" button on Known Programs cards explicitly bridges Discover to Analysis. The Builder is not yet wired into this flow — a v2 enhancement could let an Analysis result feed directly into a Builder pre-fill so the full path is one click each.

The Dashboard’s four-card grid (flagged as visually identical and unhelpful in section 5.4) is now mostly bypassed by first-time users. A returning user without active context still lands on it, which is still a problem; section 5.4’s recommendations stand.

6. Cross-cutting issues

6.1 Information architecture & navigation

  • 5 nav items, no grouping, no labels. Fine for the current footprint, but no headroom for adding features (Cover Letters? Email Templates? Saved Job Boards?) without it becoming cluttered.
  • Naming inconsistency: sidebar says "Analysis", dashboard card says "Resume Intelligence". Pick one.
  • No breadcrumbs. Not critical at current depth, but a "you are here" indicator would help once paths get longer than one level.
  • No global search. Once a user has many files and analyses, they’ll need it.

6.2 Mobile & responsive

  • One media query at max-width: 960px collapses the sidebar to a top stripe and turns 2- and 3-column grids into a single column.
  • The sidebar still renders all five nav items, the brand block, and the account card above the page content on mobile. A first-time user has to scroll past ~600px of chrome to see what they came for.
  • No mobile nav pattern — no hamburger, no bottom tab bar, no collapse.
  • No tap-friendly sizing. The .nav-link has 0.8rem 1rem padding, which is roughly 38px tall — under Apple’s 44px and Google’s 48px touch-target recommendations.
  • The 2-column form/result layouts on Analysis and Builder become two stacked very-tall blocks on mobile. The result panel can be 70vh tall and the user has to scroll past it to get back to the form.
  • Native file inputs render as tiny clipped buttons on mobile, especially on iOS Safari.
  • The Files list rows wrap awkwardly — three buttons + filename + size become four lines of unaligned text.

6.4 Brand identity

  • The brand mark is a generic anchor SVG and the word "AnchorCV" in Georgia. There’s no logo, no wordmark treatment, no monogram.

  • The marketing tagline ("AI-powered CV builder for international students") repeats verbatim in the auth panel and the sidebar — missed opportunity to introduce the product more compellingly the first time vs. as ambient context the second.
  • No imagery. No photos of students, no illustration of the workflow, no flowchart, nothing visual that says "this is for me".
  • No social proof anywhere. No "trusted by 1,000 students", no logos of partner universities, no testimonials.

6.6 Forms & inputs

  • No inline validation. Errors only appear on submit.
  • No password strength meter, no show/hide toggle, no minimum length hint.
  • Country is free text on registration.
  • Native browser color picker on the Builder page.
  • Native file input on the Files page (the FileDropzone component is at least styled, but only the two on Analysis/Builder use it).
  • Selects use system styling — the dropdown chevron, scrollbar, and option styling differ on every OS.
  • No autocomplete attributes on the auth inputs (autocomplete="email", autocomplete="current-password") — password managers behave worse than they should.
  • Textareas are fixed-rows and don’t auto-grow.

6.7 Error handling

Covered in 5.9 above. Summary: three alert()s, several inline error texts, no toast system, no global error boundary.

6.8 Animation & motion

  • One CSS animation in the entire app: @keyframes spin for the loading gear.
  • No page transitions, no card hover lifts, no entry animations on result panels, no progress animations on the storage meter, no fade-in on the spinner’s rotating quotes.
  • Hover states are static (background color change only). No transform, no scale, no shadow shift.
  • This is a major contributor to the "boring" feedback — the app feels static.

6.9 Tailwind dead weight

  • tailwind.config.js is present but the theme.extend is empty.
  • postcss.config.js exists.
  • No JSX file uses any Tailwind utility class. Every styled element is either a globals.css class or an inline style object.
  • This means: ~10MB of Tailwind preflight + utilities is being scanned and possibly emitted, with no benefit; new contributors will be misled into thinking Tailwind is the styling system; the project ships extra build dependencies (autoprefixer, postcss, tailwindcss) for no reason.
  • Decision needed: actually use Tailwind (rip out globals.css, convert components) or remove Tailwind (delete the configs and the three deps).

6.10 Copy & tone

  • The brand voice is split. Loading quotes are warm and student-friendly ("✨ Your next opportunity is one good analysis away…"). Page titles are formal and serif ("Resume Intelligence", "Profile and quota"). Error messages are technical ("Request failed.", "Invalid webhook payload.").
  • "Welcome back" hard-coded greeting (already covered).
  • "Premium" is the most overused term — it appears 11 times across the JSX. It never gets defined; it just is.
  • British vs American English: "optimised" (Builder loading quote), "Optimization" (output type label), "ATS-Optimized CV" (format label). Pick one.
  • "AI-powered CV builder for international students" is the tagline in two places. It’s descriptive but not memorable.

9. Bigger questions to answer before any redesign

If you do go further than the quick wins, decide these before drawing any new screens, because every visual decision flows from them:

  1. Is AnchorCV a one-time tool or a workspace? Right now it’s both: students arrive to do a single CV, but Files + Account suggest you want them back. The whole IA depends on which you’re optimising for.
  2. Free tier or paid-only? Currently paid-only with no preview. Adding a "preview without paying" path would dramatically improve activation but costs you margin.
  3. What’s the primary persona? "International students" is a 100M-person market with very different needs (undergrad applying to Master’s, working professional switching countries, scholar applying for funding). The product currently tries to serve all three with one UI.
  4. Should Analysis and Builder be one feature? Both upload a CV. Both produce something. A unified flow ("upload → choose what to do → result") would simplify the IA and reduce duplicated form logic.
  5. Light mode? Dark mode looks "techy" but documents (CVs) are inherently white. Many users will prefer light mode, especially in academic contexts.
  6. Mobile-first or desktop-first? The product is desktop-first today. International students apply from phones. This drives the entire layout decision.
  7. What does the brand actually feel like? Anchor (steady, dependable, nautical), AI-powered (futuristic), international students (warm, hopeful, ambitious), CV builder (professional, dry). Pick one. Right now the visuals split the difference and feel none of them.
